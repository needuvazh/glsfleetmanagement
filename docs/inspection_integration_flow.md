# Pre-Trip Dispatch Inspection Integration Flow

## Runtime Objective
The Pre-Trip Dispatch Inspection screen runs as one operational workspace that is assembled at runtime from inspection masters and transaction context. It is not a static form. The screen links to work order, fleet, trailer, driver, trip/JMP, media, approvals, dispatch readiness, and audit history.

## 1) Screen Entry Flow
When a user clicks `Create Inspection` (or opens an existing dispatch-linked inspection), the orchestration service receives:
- `work_order_id`
- `fleet_id`
- `trailer_id` (optional)
- `driver_id`
- `trip_id` or `journey_plan_id` (optional)
- `inspector_user_id`, `inspector_role`

Runtime sequence:
1. Load work order context (customer, cargo, route, stage, planned dispatch).
2. Load fleet/trailer/driver profiles and compliance snapshots.
3. Load trip/JMP context (journey approval, rest points, route controls).
4. Resolve active `Inspection Bundle` for stage `before_dispatch`.
5. Resolve active template versions mapped to the bundle.
6. Evaluate applicability rules against transaction context.
7. Produce a single composed screen model (sections, items, controls, rules).
8. Create an `Inspection Header Transaction` in `draft/in_progress` state.

## 2) Context Integration
The resolver matches runtime context against master rules. Key context dimensions:
- customer/client (PDO vs non-PDO)
- cargo type and hazardous flag
- route/site type
- site-specific requirements (H2S, permits)
- trailer presence/type
- driver qualification requirements
- JMP availability/approval

Examples:
- `trailer_present = true` -> include Trailer Safety section/items.
- `cargo_type = hazardous` -> include hazard/load security templates and rules.
- `client = PDO` -> include PDO compliance template version.
- `site_requires_h2s = true` -> include H2S permit validity check.

## 3) Master-to-UI Rendering
UI is configuration-driven from masters:
- `Bundle Master` -> one page workspace and orchestration scope.
- `Section Master` -> section cards, accordion blocks, section navigator.
- `Item Master` -> checklist rows and input controls.
- `Severity` -> row badge/color emphasis and failure prominence.
- `Media Rules` -> show photo/video capture with min/max constraints.
- `Validation Rules` -> inline errors + blockers (save/submit/dispatch/approval).
- `Approval Matrix` -> approval panel (approver, escalation, override policy).
- `Result Rules` -> computed summary status/result chips and action enablement.

No section/item should be hardcoded in screen logic.

## 4) Pre-Population from Linked Modules
The screen pre-fills headers and item values to reduce manual entry.

Header pre-fill:
- `inspection_id` generated by system
- WO/fleet/trailer/driver from linked transaction
- inspector from authenticated user
- date/time from system clock

Item pre-fill examples:
- fleet/trailer license validity from fleet/compliance modules
- driver license and H2S validity from driver module
- IVMS/DFMS availability from vehicle/device registry
- route and customer constraints from work order
- JMP approval/rest points from journey management

## 5) Transaction Design

### Inspection Header Transaction
Stores:
- `inspection_instance_id`
- `bundle_id`
- `template_version_ids`
- `work_order_id`, `fleet_id`, `trailer_id`, `driver_id`, `trip_id`
- `inspector_id`
- `current_status`, `overall_result`
- `dispatch_blocked_flag`
- `started_at`, `submitted_at`, `approved_at`

### Inspection Item Result Transaction
Stores:
- `inspection_instance_id`
- `item_id`, `section_id`
- `result`, `entered_value`, `remark`
- `severity_at_time`
- `dispatch_blocker_flag_at_time`
- `completed_by`, `completed_at`

### Inspection Media Transaction
Stores:
- `inspection_instance_id`
- `item_result_id`
- `media_type`
- `file_url`, `thumbnail_url`
- `uploaded_by`, `uploaded_at`

### Approval Transaction
Stores:
- `inspection_instance_id`
- `approver_role`, `approver_user_id`
- `decision`, `decision_comment`, `decided_at`
- `override_reason` (if applicable)

## 6) Validation Flow
Validation is layered and event-driven.

Row-level:
- fail selected but remark missing
- critical fail without required photo/video
- required field/value missing

Section-level:
- section incomplete
- minimum media evidence not met
- compliance document checks invalid

Screen-level:
- unanswered mandatory items
- critical fail present
- approval required but not completed
- dispatch blocker active

Validation trigger points:
- on value change
- on section complete/collapse
- on save draft
- on submit
- on mark passed/failed
- before dispatch release

## 7) Result and Status Calculation
Continuously compute:
- total items
- completed/passed/failed counts
- warning count
- critical failed count
- missing evidence count
- section progress
- overall result/status
- approval status
- dispatch eligibility

Result must come from `Result Logic Rules`, not from user-entered overall status alone.

## 8) Dispatch Integration
Inspection is a dispatch gate.

Rules:
- draft -> dispatch blocked
- mandatory incomplete -> blocked
- critical fail -> blocked
- pending approval -> blocked (or conditional override by rule)
- passed + approved + no blockers -> dispatch allowed

Dispatch module consumes only:
- `overall_result`
- `dispatch_blocked_flag`
- `approval_status`

Dispatch should not re-derive item-level logic.

## 9) Approval Integration
Post-submit:
1. Resolve approver from `Approval Matrix` rules.
2. Create approval task/work item.
3. Set inspection status `pending_approval`.
4. Show approval state in UI.
5. On decision, update approval transaction and dispatch eligibility.
6. If override used, enforce reason capture and audit entry.

## 10) Media Integration
Media belongs to item-result level, not only header level.

Supports:
- failed item evidence compliance
- thumbnails in review tabs
- item-level preview traceability
- corrective-action evidence linkage
- full evidence audit trail (who/when)

## 11) History and Audit Integration
History query dimensions:
- fleet, trailer, driver
- trip, work order
- inspection type, inspection bundle
- date range
- result, approval status

Audit trail records:
- created draft
- item result changes
- media uploads/deletes
- submit action
- review/approval/rejection
- override and reason

## 12) End-to-End Runtime Scenario
Scenario context:
- WO has fleet + trailer + driver assigned
- customer = PDO
- cargo loaded
- site requires H2S

Flow:
1. User opens pre-trip inspection from WO.
2. Engine resolves `DISPATCH_READY` bundle.
3. Applicability includes:
   - compliance checks (PDO)
   - trailer safety checks (trailer present)
   - load security checks (cargo loaded)
   - H2S permit item (site requirement)
4. Screen pre-fills expiry and compliance values from linked modules.
5. User completes section items; summary updates live.
6. A critical fail appears with missing evidence -> row + section + screen blockers activate.
7. Submit routes to approval workflow based on approval matrix.
8. Dispatch remains blocked until rule conditions are cleared (or approved override path is completed).
9. Final transactions, media, approval decision, and audit events are stored and queryable in history.

## Engineering Outcome
This integration model is sufficient to implement:
- dynamic one-screen inspection UI
- context-based composition from masters
- transaction persistence
- layered validations
- approval orchestration
- dispatch gating
- item-level media traceability
- searchable history and full audit compliance
